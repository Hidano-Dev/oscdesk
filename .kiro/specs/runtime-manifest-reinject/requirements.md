# Requirements Document

## Project Description (Input)

### 一文要約

Unity の `OscSurfaceBridge` が **有効化後(Play 中)にマニフェストを差し替え、staging 計画を組み直して `/sys/manifest` を再送できる**ようにする。あわせて、フォーク a8-oscdesk が先行実装している実行時マニフェスト注入 API(F-5 `SetManifestAsset` / F-6 `SendManifestNow`)を本リポジトリへ取り込む。エントリの増減を伴う再注入を、ブリッジ・UI・mock-unity が破綻なく扱えることもテストで保証する。

### 背景(フォーク a8-oscdesk からの要望、2026-09-29)

フォーク a8-oscdesk は VP コンサートプリセットを使っており、MotionBuilder(以下 MB)の接続先を `/vp/mb/{KK}/*` として MB 件数分マニフェストに並べている。現場から「ブラウザ UI から MB マシンを追加・削除したい」という要望が出た。フォーク側で決まっている運用は次のとおりである(フォーク spec `oscdesk-mb-endpoint-list` の改訂版)。

- 追加は UI の追加フォーム(種類・address・port・追加ボタン)から行う。Unity は受け取った値で実機設定(NodeTranslator の接続先一覧、Crescent プラグインの実体)を即時に変え、その実状態からマニフェストを組み直して再送する。Unity が真実の源である
- 行ごとの種類・active・address・port・削除の変更は staged で、MB Sync(適用トリガ)でまとめて確定する。削除が確定すると後ろの行の番号が詰まる
- MB 件数の上限は 4 件。マニフェストのワイヤサイズを実用上限 60 KiB に収めるため

つまり **Play 中にマニフェストのエントリ集合(件数)が変わる**。本リポジトリの `OscSurfaceBridge` は `Awake` で staging 計画を一度だけコンパイルし、その後マニフェストを差し替える口を持たないため、これを実現できない。

### 現状の機構

- 本リポジトリの `OscSurface/Assets/OscSurfaceBridge/OscSurfaceBridge.cs` は、`Awake` でアセット検証 → 宣言写像 → `StagingPlan.TryCompile` → 初期値シードを **一度だけ** 行う。以後、計画(`StagingEngine`)とアセットは固定である。`/sys/manifest` は `/sys/manifest/request` への応答と接続時にだけ送る
- フォーク a8-oscdesk は次の 2 つの公開 API を追加実装済みで、upstream への取り込みを要望している(フォーク `docs/UPSTREAM_FEEDBACK_HOST_MIGRATION.md` F-5 / F-6)。本リポジトリには **まだ無い**
  - F-5 `bool SetManifestAsset(OscSurfaceManifestAsset asset)`: `Awake` より前(非アクティブな GameObject に AddComponent した直後など)にだけアセットを差し替えられる。消費済み(`Awake` 後)や null の場合は拒否して false を返す
  - F-6 `bool SendManifestNow()`: 現在のアセット内容で `/sys/manifest` を自発送信する。非アクティブ時、staging 宣言が不正で抑止中のとき、アセットが不正なときは false を返す
- フォークは Play 中の MB 接続先の **値** の変化を、`uOscServer.onDataReceived.Invoke` を使ってブリッジへ自己注入して反映している(フォークの暫定策。受信統計 `received` に自己注入分が混ざる)。フォークはこれを公開 API に置き換える要望 F-7 を持っている
- ブリッジは新しいマニフェストを採用するたびに `adoption` を更新する。UI は新しい採用のたびに、ホールド中でないチャネルを `default` へ強制再同期する(D-037)。内容が同一の採用では、編集中(ホールド中)の input を上書きしない。内容が変わった採用では、本体を再描画する前に全ホールドを送信せずに打ち切る(`SurfaceState._on_manifest` の `cancel_all_holds()`。保留中の間引き値と下書きも捨てる)。このため、編集中の値も新しい `default` で上書きされる
- ワイヤサイズの規則(D-038): `MANIFEST_SIZE.WARNING_BYTES = 56 KiB` を超えたときは通知だけで、配信は続ける。`PRACTICAL_LIMIT_BYTES = 60 KiB` は単一データグラムに載る実用上の上限である。ただし、現状どの経路でも送信の拒否には使っていない。mock-unity は超過時にログを出すだけで、Unity の `SendManifest` にはサイズ検査が無い(ブリッジの `udp-transport` の拒否は、UI からの OSC 送信のバッチに対するものである)
- Unity の `OscSurfaceBridge.HandleNormalMessage` は、`/sys/*` 以外の受信をすべてエコーする。アドレスが staging 計画にあるかどうかは確かめない(未知のアドレスも正規化してそのまま返す)

### 要求する挙動(要件化の材料)

1. **F-5 / F-6 の取り込み**: フォークの追加差分(`SetManifestAsset` / `SendManifestNow` と `manifestAssetConsumed` の管理)を本リポジトリへ取り込む。既存の `Awake` / `OnEnable` / `/sys/*` 応答 / エコーバック / `ApplyRequested` の挙動は変えない
2. **有効化後のマニフェスト再注入(F-8)**: 有効化後(`Awake` 後)でもマニフェストアセットを差し替えられる公開 API を足す。差し替えでは次を行う
   - 新しいアセットを検証し、staging 宣言を再コンパイルする
   - 失敗したら、**旧アセット・旧計画・旧現在値をそのまま維持**して false と理由を返す。ブリッジを止めず、`/sys/manifest` も送らない
   - 成功したら計画を差し替える。旧計画の現在値(staged の未適用値を含む)は、下記の引き継ぎ規則で「同じ実体」と判定したエントリにだけ引き継ぐ。それ以外のエントリ(消えたもの、新しく現れたもの、同じアドレスでも別の実体になったもの)は、新しいアセットの `default` でシードする。そのうえで `/sys/manifest` を再送する(当初案は「同じアドレスなら引き継ぐ」だったが、番号の詰まりで誤りになるため、下記の規則を要件化で決めることにした)
   - Play 中に何回呼んでもよい
   - **再注入のマニフェストが届かなかったときに回復できること(PR #4 レビュー P1)**。再注入で送る `/sys/manifest` は UDP のデータグラム 1 通である。ブリッジは一度マニフェストを受理すると問い合わせをやめる(`ManifestClient` が `settled` になり、`shouldRequest()` が false を返す)。UI の `manifestRequest` には、手元に保存している旧マニフェストで答える(`surface-core.ts` の `handleUiFrame`)。そのため、この 1 通が失われると、Unity は新しい計画で動いているのに、UI は旧い構造のまま戻らない。その間、旧い行から送られた値が新しい計画に作用してしまう。取りこぼしを検出して再取得する仕組みを要件にする。候補は次のとおり(どれも `/sys/*` のアドレス体系は変えない。対象外を参照)
     - マニフェストの世代やハッシュを、既存の `/sys/stats` の JSON に載せる。ブリッジは受理済みのものと食い違いを検出したら、`/sys/manifest/request` で取り直す(既存のアドレスのペイロードに項目を足す変更なので、`docs/UNITY_PROTOCOL.md` に互換性ノートを残す)
     - ブリッジが `settled` の後も、一定間隔で `/sys/manifest/request` を送って照合する
     - Unity が再注入のたびに、`/sys/manifest` を間隔を空けて複数回送る(取りこぼしの確率を下げるだけで、回復は保証しない。単独では不十分)

     受け入れには、再注入で最初に送るデータグラムを落とし、UI が新しい構造へ追いつくことを確かめるテストを含める
   - **遅れて届いた旧い世代のマニフェストを採用しないこと(PR #4 レビュー P1)**。UDP では順序も保証されない。再注入前の `/sys/manifest/request` への応答が、再注入のマニフェストより後に届くことがある。ブリッジは正しい形のマニフェストをすべて新しい採用として受理する(`surface-core.ts`)。そのため、遅れた旧いマニフェストで UI が旧い構造に戻り、Unity は新しい計画のまま、という状態になる。定期的な照合で最終的には追いつくとしても、それまでの間に旧い行の値が再利用アドレスへ作用しうる。マニフェストに、単調に増える世代を持たせる。ブリッジは受理済みより古い世代を捨てることを要件にする(`/sys/manifest` の JSON に項目を足すので、`packages/shared` のスキーマと `docs/UNITY_PROTOCOL.md` の互換性ノートを更新する。世代を持たない既存の送信元との互換も決める)。上の「取りこぼしからの回復」と同じ世代を使ってよい。受け入れには、次の順序のテストを含める。旧い応答を受理する → 新しいマニフェストを受理する → 遅れた旧い応答が届く → 捨てられる
     - **世代は Unity の再起動をまたいで比較できること(PR #4 レビュー P1)**。メモリ上のカウンタだけでは、ブリッジが世代 N を受理した後に Unity が再起動すると、カウンタが初期値に戻る。すると、新しい Unity のマニフェストがすべて「古い」と判定され、UI が旧い構造のまま戻らない(到達不能への遷移を経ずに再起動が終わった場合も含む)。また、「エポックが変われば受理する」だけでは、起動をまたいだ新旧が決まらない。再起動後のエポック B を受理した後に、再起動前のエポック A の遅れたデータグラムが届くと、これも「エポックの変化」に見えて受理され、UI が A の旧い構造に戻ってしまう(PR #4 レビュー P1)。そこで世代について、方式ではなく次の不変条件を要件にする。方式は design で決める
       - ブリッジの 1 回の稼働の間、受理するマニフェストの世代は、Unity の再起動をまたいでも全順序で単調に進む。一度受理した世代より前のものは、別の起動のものも含めて受理しない
       - Unity の再起動後の最初のマニフェストは受理される(再起動前の世代より前と判定されない)
       - 方式の候補: 起動をまたいで順序が付くエポック(永続化したカウンタ、起動時刻など。時刻を使う場合は時計の巻き戻りへの扱いを決める)とカウンタの組を辞書順で比較する / 再起動を確認したときだけ新しいエポックを受け入れ、その稼働中に退役したエポックを以後すべて拒否する

       受け入れには、次の 2 つの順序のテストを含める。(a) 再注入の後に Unity を再起動し、UI が新しい Unity の構造へ追従する (b) エポック A を受理する → 再起動後のエポック B を受理する → A の遅れたデータグラムが届く → 捨てられる
     - **構造の世代と値の版を分け、どちらも「より新しいか」だけで採否を決めること(PR #4 レビュー P1、下の 3 項目の統合)**。下の 3 項目(同じ世代の重複、世代を進める契機、到達性回復時の再同期)は、同じ世代の応答を「重複として捨てる」か「再同期に使う」かを、応答の種類で区別しようとした。しかし `/sys/manifest/request` には要求 ID が無く、応答にも対応付けの項目が無い。そのため、到達性を失う前に送った通常の照合の応答が、回復後の要求の直後に届くと、ブリッジはこれを回復の応答と区別できない。古い値で再同期してしまい、その後に届く本当に新しい応答を重複として捨てる。結果、UI は古い値のまま、後の適用で Unity の状態を上書きしうる。そこで、応答の種類による例外は設けず、マニフェストに次の 2 つの版を持たせることを要件にする(どちらも上記の不変条件と同じく、Unity の再起動をまたいで全順序で比較できること)
       - 構造の世代: 下の「世代を進める契機」の規則で進める(F-8 の確定の成功、F-6 による内容の変わった公開)
       - 値の版: Unity の中核の現在値が変わるたびに進める(受信による記録、展開書き込み、適用、F-8 のシード、F-7 を入れる場合はその注入を含む)。マニフェストの `default` は、その値の版の時点の現在値である

       ブリッジの採否: 構造の世代が受理済みより新しければ、構造の再採用として扱う(UI は再描画する)。構造の世代が同じで値の版が新しければ、値だけの再同期として扱う(UI は再描画せず、ホールドも打ち切らず、ホールド中でないチャネルを `default` へ再同期する)。どちらも新しくなければ捨てる。応答が回復の要求に対するものかどうかは問わない。
       - **値の版は、通常のエコーとも新旧を比べられること(PR #4 レビュー P1)**。マニフェストだけに値の版を持たせると、エコーとの順序が決まらない。例: Unity が値 A を含む値の版 1 のマニフェストを組み立てる → 値 B を記録して値の版 2 にしてエコーする → UDP でエコー B が先に届き、UI が B を確定する → 遅れた版 1 のマニフェストが届き、値だけの再同期で A に戻る → 後の適用で A が Unity を上書きする。エコーには版が無いので、ブリッジは比べられない。要件化では、次のどれかを決める
         - エコーにも値の版(またはアドレスごとの版)を付ける。OSC 1.0 標準の範囲で表す(例: 引数の追加、またはタイムタグ付きのバンドル)。既存のエコーの形式の変更になるので、他の OSC 受信側(TouchOSC など)への影響と、`docs/UNITY_PROTOCOL.md` の互換性ノートを伴う
         - マニフェストの値の版とは別に、ブリッジがアドレスごとに「最後に確定したエコーより前に組み立てられたマニフェストの値」を捨てられるだけの情報を、マニフェストに載せる(例: エントリごとの値の版)。その場合もエコー側に比較できる版が要るかを確かめる
         - 値だけの再同期を行わない(構造の再採用時だけ `default` へ再同期し、到達性回復時の値の追従は別の方法で行う)。その場合、回復時に値が追従する要件(下の「到達性回復時の値の再同期」)との両立を示す

         なお、エコーどうしの順序の入れ替わり(同じアドレスの 2 つのエコーが逆順に届く)は、この spec 以前から UDP で起こりうる既存の制約である。この spec で解消するかどうかも、あわせて決める。受け入れには、選んだ方式について、次の順序のテストを含める。値の版 1 のマニフェストを組み立てる → 値 B を記録してエコーする → エコー B が先に届く → 版 1 のマニフェストが届く → UI は B のまま
       
       受け入れには、次の順序のテストを含める。到達性を失う前に送った照合の応答が遅れる → 到達性を失う → Unity 側の値が変わる → 回復して取り直す → 遅れた旧い応答が先に届く(捨てられる) → 新しい応答が届く(値が再同期される)
     - **同じ世代の再受信を新しい採用として扱わないこと(PR #4 レビュー P2)**。`/sys/manifest` の `default` は中核の現在値を埋めるため、同じ世代でも値が変わると内容が変わる。取りこぼし回復のために定期的に照合する案を選んだ場合、照合の応答のたびに内容が変わったと判定される。すると UI が再描画して編集中の入力を打ち切り、再注入が無くても編集が消え続ける。ブリッジは受理済みと同じ世代・同じ値の版のマニフェストを、内容の比較ではなく版で重複と判定して、再採用しない(新しい `adoption` を発行しない)ことを要件にする。「Unity が同じ世代では同じペイロードを返す」だけでは不十分である(PR #4 レビュー P1)。UI は、内容が同一でも新しい採用のたびに、ホールド中でないチャネルを `default` へ強制再同期する。そのため、保存しておいた旧い `default` を再送すると、照合のたびに表示が旧い値へ戻り、後の適用でその旧い値が Unity へ送り返されてしまう。受け入れには、定期照合で同じ版(構造の世代・値の版とも同じ)のマニフェストを再受信しても、編集中の入力が打ち切られず、表示値と適用セットの値も変わらないテストを含める(値の版が新しい場合は、上の規則どおり値だけを再同期する)
     - **世代を進める契機を定めること(PR #4 レビュー P1)**。世代は「論理的な内容の公開」1 回につき 1 回だけ進める。進めるのは、F-8 の確定の成功と、F-6 `SendManifestNow` による内容の変わった公開(例: `optionLists.devices` の更新)である。`/sys/manifest/request` への応答、回復のための再送、起動時・接続時の送信は、現在の世代をそのまま使う。F-6 で世代を進めないと、ブリッジが同じ世代として捨てるので、`SendManifestNow` は成功を返すのに UI が更新されない。逆に、共通の送信経路の中で毎回進めると、要求への応答のたびに新しい採用になり、UI の状態が繰り返しリセットされる。受け入れには、フォーク文書の F-6 の利用例(`optionLists.devices` を更新して `SendManifestNow` を 1 回呼ぶ → UI の選択肢が更新される → その後の `/sys/manifest/request` への応答では再採用が起きない)のテストを含める
     - **到達性回復時の値の再同期は、同じ世代でも行うこと(PR #4 レビュー P1)**。現状のブリッジは、到達性の喪失から回復すると、マニフェストを取り直す(`surface-core.ts` の pong 処理で `manifests.onReachabilityRecovered()` → `requestManifest()`)。この応答の `default`(中核の現在値)で UI の値を再同期する。途絶中に Unity 側の値が F-6 / F-8 を経ずに変わっていても、これで UI が追いつく。同じ世代を一律に捨てると、この応答も捨てられて新しい採用が起きず、UI が旧い値を保持したまま、後の適用で Unity の状態を上書きしうる。この再同期は、上の「構造の世代と値の版」の値の版で実現する(応答の種類で区別する方式は、要求 ID が無いため遅れた旧い応答と区別できず、採らない)。受け入れには、次の順序のテストを含める。到達性を失う → Unity 側の値が変わる → 回復する → 同じ世代の応答で UI の値が新しい値へ再同期される
   - **再注入では `projectId` を変えないこと(PR #4 レビュー P1)**。ブリッジは、設定の `expectedProjectId` と異なる `projectId` のマニフェストを拒否し、受理済みの旧マニフェストを保持し続ける(`ManifestClient.onManifestPayload`)。F-8 が別の `projectId` のアセットで差し替えに成功すると、Unity は新しい計画で動き、UI は旧いまま戻らない。この食い違いは再送や再取得では解消しない。F-8 は、現在の `projectId` と異なるアセットを拒否して、理由を返すことを要件にする(`projectId` の変更はブリッジの設定変更を伴うので、再注入の対象外とする)。受け入れには、この拒否のテストを含める
   - **ホストの実状態の変更と、再注入をそろえて成功・失敗させること(PR #4 レビュー P1)**。フォークの追加の流れでは、Unity が先に実機設定(NodeTranslator の接続先、Crescent の実体)を変え、その実状態からマニフェストを組み直して F-8 を呼ぶ。このとき F-8 が失敗すると(検証エラー、コンパイルエラー、サイズ超過、`projectId` の不一致)、旧い計画が残る。実状態と、UI に出ている操作項目が食い違い、「Unity が真実の源」に反する。F-8 側では、差し替えを確定せずに候補を検査できる事前検査(検証・コンパイル・シード後のサイズ測定・`projectId` の照合を、差し替えと同じ判定で行う)を公開する。ホストが実状態を変える前にこれを呼べることを要件にする。事前検査が通った後の確定は、同じ候補に対して失敗しないことを保証する(または確定が失敗した場合の理由を区別して返し、ホストが実状態を戻せるようにする)。実状態の巻き戻しそのものはフォーク(ホスト)の責務である。その契約(呼ぶ順序と失敗時の扱い)を `docs/UNITY_PROTOCOL.md` に記録する。受け入れには、「ホスト側の変更を準備したが、事前検査で失敗する」場合のテストを含める。この事前検査は、要求 4 のサイズ測定の公開を包含してよい
   - 型が変わった同一アドレス(例: `i` → `s`)の扱いは設計で決める(引き継がず `default` でシードする案が有力)
   - **アドレスだけで値を引き継ぐと誤りになる場合があり、要件化で規則を決める(PR #4 レビュー P1)**。中間の行を削除して後ろの行の番号が詰まると、同じアドレスが別の実体(別の MB マシン)を指すようになる。旧アドレスの現在値や staged 値をそのまま引き継ぐと、前にその番号にいた実体の設定を配信してしまう。これは、Unity が実状態から組み直した新しい `default` を上書きすることであり、「Unity が真実の源」に反する。少なくとも次のどれかを選ぶ
     - エントリに安定した識別子を持たせ、識別子が一致する場合だけ引き継ぐ
     - ホストが、引き継ぐかどうかを再注入の引数で指定する(例: 引き継がないアドレスの集合、または全件 `default` でシード)
     - 引き継ぎをやめ、常に新しいアセットの `default` でシードする。未適用の staged 値はホスト側で組み直した `default` に反映してもらう
   - **引き継いだ値は UI に見えなければならない(PR #4 レビュー P1)**。UI は内容が変わった採用で、全チャネルをマニフェストの `default` へ強制再同期する(`SurfaceState._on_manifest`)。一方、`/sys/manifest` の JSON(`TryBuildManifestJson`)の `default` は、アセットの値ではなく、中核の現在値(`stagingEngine.TryGetCurrentValue`)を埋めたものである(`OscSurfaceBridge.cs` の `TryBuildManifestJson`)。したがって、次の順序を守れば、引き継いだ値(staged の未適用値を含む)はそのまま UI に見える。追加の同期経路(エコーでの再送やアセットの書き換え)は要らない。この順序を要件にし、テストで固定する
     1. 新しい計画をコンパイルする
     2. 引き継ぎ規則に従って、新しい計画に現在値をシードする
     3. 計画を差し替える
     4. `/sys/manifest` を組み立てて送る

     順序を誤り、差し替え前の計画やシード前の計画からマニフェストを組み立てると、UI に表示される値と、後の `ApplyRequested` で確定する値が食い違う。「常に `default` でシードする」案を選んだ場合は、引き継ぐ値が無いので、この問題は起きない
3. **F-6 と F-8 の整合(PR #4 レビュー P1)**: フォーク版の `SendManifestNow` は、現在のアセットを検証し直してから送るだけで、staging 計画を再コンパイルしない。ホストが `SetManifestAsset` に渡したアセットを保持しておき、`Awake` 後に `entries` を書き換えて `SendManifestNow` を呼ぶと、UI には新しい構造のマニフェストが届く。一方、通常受信と `ApplyRequested` は旧計画のまま動く。この経路は F-8 のトランザクション(失敗時の維持)とサイズ検査を素通りする。要件化では次のどちらかを決める
   - 消費時にアセットを複製・凍結し、後から外部で書き換えても影響しないようにする
   - `SendManifestNow` は、計画に影響する構造変更を検出したら拒否する。構造変更は F-8 経由に限る

   あわせて、フォーク側の利用例(`optionLists.devices` の差し替え → `SendManifestNow`)が、どちらの案でも成り立つかを確かめる
4. **再注入時のサイズ検査**: 再注入の前に、新しいアセットのワイヤ JSON の UTF-8 バイト数を測れるようにする。`PRACTICAL_LIMIT_BYTES` を超える再注入は拒否し、理由を返す。フォークは MB の追加を受け付ける前に、組み直した後のサイズを確かめたい。測定 API を公開するか、再注入の戻り値に理由を載せるかは設計で決める
   - **測る対象は、シード済みの候補から組み立てた実際のペイロードとする(PR #4 レビュー P2)**。`/sys/manifest` の `default` は中核の現在値から埋める(要求 2)。そのため、アセットだけを測ると、引き継いだ長い文字列の値などが計算に入らず、60 KiB 未満と判定したのに実際の送信は超過する、ということが起こりうる。サイズ検査は、新しい計画をコンパイルして引き継ぎ値をシードした候補から、`TryBuildManifestJson` と同じ方法で JSON を組み立てて測る。計画の差し替えは、その結果を見てから行う。受け入れのサイズ超過のテストには、「アセット単体では上限未満だが、引き継いだ大きな値を含めると超過する」場合を含める
   - **拒否は F-8 で新しく導入するポリシーである(PR #4 レビュー P2)**。現状では、起動時の送信・`/sys/manifest/request` への応答・`SendManifestNow` のどれにも拒否がない。F-8 だけで拒否すると、同じサイズ超過のマニフェストが、ある経路では配信され、別の経路では拒否されることになる。F-8 限定の新ポリシーとして記録するか、全送信経路で一貫させるか(既存の経路の挙動変更になる)を要件化で決める
5. **値注入 API(F-7、要否は要件化で判断)**: ホストが Unity 側の実状態の変化(Inspector 編集、実機の変化)を、受信経路を偽装せずにブリッジの現在値へ反映し、エコーバックできる公開 API。受信統計には計上しない。F-8 と同時に入れるか、別 spec にするかを requirements で決める
6. **ブリッジ / UI の追従の保証**: エントリの増減・番号の詰まりを伴う再採用を、ブリッジと UI が正しく扱うことをテストで保証する。特に次の 3 点を決めて、テストで固定する
   - 編集中の値を保護する規則と、再採用でアドレスの意味が変わる場合との整合。例: 削除で番号が詰まり、編集中の `/vp/mb/03/address` の値が、別の接続先を指すようになった行に残る恐れがある。UI の現状の実装は、内容が変わった採用では全ホールドを打ち切っている(上記「現状の機構」)。この挙動をテストで固定し直すか、エントリ単位の規則へ細かくするかを決める。2 の値の引き継ぎ規則(Unity 側)と矛盾しないようにする
   - 再採用で消えたアドレスへの UI の送信を、ブリッジと Unity がどう扱うか。現状の Unity は未知のアドレスもエコーする(上記「現状の機構」)ため、消えたアドレスに届いた遅れた送信は UI へエコーされる。この挙動を仕様として受け入れるか、F-8 で計画外のアドレスをエコーしないように変えるかを決める。変える場合は、既存のエコーバックの挙動の変更として `docs/UNITY_PROTOCOL.md` に記録する
   - **再利用されたアドレスに、遅れて届く送信の扱い(PR #4 レビュー P1)**。番号が詰まって `/vp/mb/03/*` が別の実体に再利用されたとき、UI が旧採用の下で送った送信がまだ届いていない場合がある(UI → ブリッジ → Unity の途中にある)。この送信は、新しい計画にも存在するアドレス宛てなので「消えたアドレスへの送信」には当たらない。Unity の `HandleNormalMessage` は、これを新しい実体の値として記録し、エコーしてしまう。UI 側でホールドを打ち切っても、すでに送り出したデータグラムは取り消せない。旧い行の値が新しい実体を書き換えないように、アドレスを再利用するときの移行規則を要件にし、テストで固定する。候補は次のとおり
     - アドレスを再利用しない: 行のアドレスを番号でなく安定した識別子にする(この場合、フォーク側のアドレス設計の変更が要る。要求 2 の「安定した識別子」案と揃う)
     - 世代で区別する: 採用ごとの世代を送信に持たせ、Unity は旧世代の送信を捨てる(OSC 1.0 標準の範囲で表現でき、`/sys/*` のアドレス体系を変えない方法に限る。対象外の「`/sys/*` のアドレス体系の変更」に触れないこと)
     - 静止期間(一定時間、または UI の採用確認まで受信を捨てる)は**候補にしない**(PR #4 レビュー P1)。UDP のデータグラムは、固定の時間や逆方向を通る確認より遅れて届くことがあり、ゲートが再び開いた後に届いた旧い送信は、新しい実体の値として記録されてしまう。遅延の上限に依存せずに旧い送信を区別できる方式(上の 2 案、または順序が保証された排出の手続き)に限る

   どの案でも、「旧採用の下での送信 → 再注入(アドレスの再利用) → その送信が Unity に届く」という順序で、新しい実体の値が変わらないことをテストする。届くまでの遅延を任意に長くした場合(移行の手続きが完了した後に届く場合)も含める
7. **mock-unity の開発用の口(要否は要件化で判断)**: E2E で「Play 中にエントリ集合が変わる」経路を検証できるように、mock-unity のシナリオで実行時にマニフェストを差し替えて再送できるようにする(例: 特定のトリガを受けたら別シナリオのエントリ集合に切り替える)。案件固有の意味論(MB の追加・削除そのもの)は持ち込まない

### 対象外

- 案件固有の意味論(MB の種類、追加・削除の規則、NodeTranslator / Crescent への反映)。これらはフォークの担当である
- `/sys/*` のアドレス体系の変更
- ワイヤサイズの閾値の再議論(D-038 で決着済み)
- マニフェストの分割送信(サイズ上限そのものを引き上げる仕組み)

### 受け入れの観点

- Unity EditMode:
  - 再注入の成功と失敗(検証エラー、staging コンパイルエラー、サイズ超過、`projectId` の不一致)。失敗時に旧状態が維持されること。事前検査が、差し替えと同じ判定を返すこと。サイズ超過には、引き継いだ値を含めて初めて超過する場合を含める
  - アドレスが再利用されたとき、旧採用の下で送られて遅れて届いた送信が、要求 6 で選んだ移行規則どおりに扱われ、新しい実体の値を変えないこと。移行の手続きが完了した後に届いた場合も含める
  - 現在値(staged の未適用値を含む)の引き継ぎが、要求 2 で選んだ規則どおりになること。「同じ実体」と判定したエントリだけが引き継がれ、それ以外のエントリは `default` でシードされること。番号が詰まる場合(中間の行を削除し、後ろの行が同じアドレスを再利用する)で、前にその番号にいた実体の値が新しい実体に残らないこと
  - 適用トリガの `appliesTo` が、新しい計画のアドレス集合で解決されること
  - F-5 / F-6 の既存の受け入れ条件(フォーク文書 F-5 / F-6 の「受け入れ条件」)
- ブリッジ / UI: 再注入で最初に送る `/sys/manifest` のデータグラムを落としても、要求 2 で選んだ回復の仕組みによって、ブリッジと UI が新しいマニフェストへ追いつくこと
- ブリッジ / UI: 次の順序で、遅れた旧い応答が捨てられ、UI が新しい構造のままであること。旧い応答を受理する → 新しいマニフェストを受理する → 遅れた旧い応答が届く
- ブリッジ / UI: 再注入の後に Unity が再起動しても(世代のカウンタが初期値に戻っても)、UI が新しい Unity の構造へ追従すること。再起動前の起動(エポック A)の遅れたデータグラムが、再起動後(エポック B)の受理の後に届いても捨てられること
- ブリッジ / UI: F-6 で `optionLists.devices` を更新して `SendManifestNow` を 1 回呼ぶと、世代が 1 回進んで UI の選択肢が更新されること。その後の `/sys/manifest/request` への応答では世代が進まず、再採用が起きないこと
- ブリッジ / UI: 到達性を失っている間に Unity 側の値が変わっても、回復後に取り直した同じ世代(新しい値の版)のマニフェストで、UI の値が再同期されること。その前に、到達性を失う前の照合の応答(古い値の版)が遅れて届いても捨てられること。値だけの再同期では、再描画もホールドの打ち切りも起きないこと
- ブリッジ / UI: 構造の世代も値の版も同じマニフェストを再受信しても(同じペイロードの再送、遅れた重複を含む)、ブリッジが新しい採用を発行せず、編集中の入力が打ち切られず、表示値と適用セットの値が変わらないこと。値の版だけが新しいマニフェストでは、再描画もホールドの打ち切りも起きず、ホールド中でないチャネルだけが新しい値へ再同期されること
- ブリッジ / UI: 値の版 1 のマニフェストより後に記録された値 B のエコーが先に届き、その後に版 1 のマニフェストが届いても、UI が B のままであること(要求 2 で選んだエコーとの順序付けの方式で)
- ブリッジ / UI: エントリの増減を伴う再採用で、UI が行を増減し、編集中の値の扱いが要求 6 で決めた規則どおりになること。消えたアドレスへの送信の扱い
- ブリッジ / UI: staged の未適用値を引き継ぐ規則を選んだ場合、次の順序で UI の表示と Unity の現在値が一致すること。値を staged にする → 構造が変わる再注入を行う → 再採用で UI が再同期する → `ApplyRequested` を送る。このとき、UI に表示されている値と、`ApplyRequested` で確定する値が同じであること
- `docs/UNITY_PROTOCOL.md` に再注入の意味論(値の引き継ぎ・失敗時の維持・サイズ検査)を互換性ノートとして記録する。`docs/VERIFICATION.md` に手動検証の手順を追記する
- 既存のテスト一式(`corepack pnpm test`、Unity EditMode)が緑のまま
