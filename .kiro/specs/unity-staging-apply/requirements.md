# Requirements Document

## Project Description (Input)
unity-staging-apply: Unity 側参照実装(OscSurface/Assets/OscSurfaceBridge/ の OscSurfaceBridge / OscSurfaceManifestAsset)に「受信値を蓄えて Update ボタン受信時にアプリへ適用する」ステージング機能を追加する。ワイヤプロトコルは無改造(マニフェスト version: 1 のまま)で、UI から見れば通常のエコーバック付き送信と区別がつかない設計により、既存の UI・ブリッジ・プロトコルを一切変えずにレガシー(VP_OscClient)の「Update ボタンを押した時だけ反映」という運用感を再現する。ステージング構成(対象・適用トリガ・一括操作の展開規則)は C# を書き換えずアセット定義だけで宣言できること。mock-unity へのステージング挙動の模擬と docs/UNITY_PROTOCOL.md への追記を含む。要件の正は docs/LEGACY_PRESET_REQUIREMENTS.md §6.3(R3)。詳細な背景・決定済み事項・スコープ・未決事項は .kiro/multi-spec/legacy-preset-upstream.md の「全体コンテクスト」「共通の決定済み事項」「Spec: unity-staging-apply」の各節に記載されており、requirements 生成・dig インタビュー・design の前提として必ず読み込むこと。関連 spec: .kiro/specs/manifest-input-select-widgets/ も参照(同一ファイル docs/UNITY_PROTOCOL.md・mock-unity・OscSurfaceBridge/*.cs を変更するため)。

## Introduction

本仕様は、Unity 側参照実装(`OscSurface/Assets/OscSurfaceBridge/` の `OscSurfaceBridge` / `OscSurfaceManifestAsset`)に **ステージング(蓄えて適用)機構** を追加する。

現行の参照実装は、通常メッセージを受信すると即座に `currentValues` へ記録し同一アドレスへエコーバックする(`docs/UNITY_PROTOCOL.md` §4.3)。この挙動では「値を編集した瞬間にアプリへ反映される」ため、レガシー版 VP_OscClient の「各フィールドを編集しても、Update ボタンを押すまではキャラクターに反映されない」という運用感を再現できない。

本機能は、ステージング対象として宣言されたアドレスの受信値を **ステージング領域に保持するだけ** にとどめ、適用トリガ(button)を受信した時点で対象範囲の値をアプリケーションへ適用するイベントを発火する。UI から見た挙動(即時エコーバックによる表示確定)は従来と一切変わらないため、ワイヤプロトコル・ブリッジ・NiceGUI UI は無改造で済む(per plan S2-1)。

要件の正は `docs/LEGACY_PRESET_REQUIREMENTS.md` §6.3(R3)であり、関連節として §3(D-L3)・§4.2(レガシー挙動との対応表)・§5(共通前提)・§6.4(非機能)を参照する。分割とセッション固有の決定は `.kiro/multi-spec/legacy-preset-upstream.md` に従う。

## Boundary Context

- **In scope**:
  - `OscSurfaceManifestAsset` への宣言追加: ステージング対象、適用トリガ(button エントリの適用範囲)、一括操作の展開規則。**C# を書き換えずアセット定義だけで構成できること**
  - `OscSurfaceBridge` の受信時挙動: ステージング領域への保持、同一アドレスへの通常どおりのエコーバック、`currentValues`(マニフェスト `default` の供給源)のステージング値での更新
  - 適用トリガ受信時に、対象範囲のステージング値をアプリケーションへ適用させるコールバック/イベントの発火(適用処理自体はアプリ固有実装に委ねる)
  - 一括操作(1 アドレス受信 → 複数アドレスへの書き込み)の展開と、展開先各アドレスへの個別エコーバック
  - 適用前ステージング値と適用済み値の乖離の許容
  - mock-unity へのステージング挙動の模擬
  - `docs/UNITY_PROTOCOL.md` §4(実装指針)・付録 A・互換性ノートへの追記、`docs/VERIFICATION.md` への手動検証手順追記
- **Out of scope**:
  - input / select ウィジェット(R1 / R2、要件書 §6.1・§6.2)— 先行 spec `manifest-input-select-widgets` が担当済み
  - 適用処理そのもの(キャラクターへの反映など。BasicConcertDevelopment_URP 側の構成はフォーク側 §7-3 の作業)
  - ワイヤプロトコル・ブリッジ(`packages/bridge`)・NiceGUI UI・共有スキーマ(`packages/shared`)の変更(per plan S2-1, G-4)
  - フォーク側成果物: 64 スロットのデフォルトプリセットアセット、`vp-concert-default` シナリオ、E2E(per plan G-5)
  - 入力値の形式検証(`pattern`)— 先行 spec で UI 側に実装済みのため、本 spec に「形式不正の値をステージングで無視する」受け皿要件は設けない
- **Adjacent expectations**:
  - `docs/UNITY_PROTOCOL.md`・mock-unity・`OscSurface/Assets/OscSurfaceBridge/*.cs` は先行 spec `manifest-input-select-widgets` も変更する。推奨順(#1 → #2)の順次実行でコンフリクトを避ける
  - 本 spec が提供するのは **機構** のみであり、`/vp/member/{NN}/*` などの具体アドレス構成はフォーク側がアセット定義(データ)として与える
  - 先行 spec が拡張した `OscSurfaceManifestAsset`(input / select / options / optionsRef / optionLists)の上に、本 spec のステージング宣言を追加する

## Requirements

### Requirement 1: ステージング構成のアセット宣言
**Objective:** Unity 側の案件担当者として、ステージング対象・適用トリガ・一括操作の展開規則をアセット定義だけで宣言したい。それにより、案件ごとに C# を書き換えることなく「蓄えて Update で適用」の構成をデータで組める。

#### Acceptance Criteria
1. The マニフェスト定義アセット(`OscSurfaceManifestAsset`)shall エントリ単位のフラグ(`staged`)で「ステージング対象」を宣言する手段を提供する(per plan S2-2、要件書 R3-1、see D-10)。
2. The マニフェスト定義アセット shall button エントリに「適用トリガ」としての適用対象範囲を、OSC アドレスのワイルドカードパターンで宣言する手段を提供する(要件書 R3-1、see D-10, D-15)。
3. The マニフェスト定義アセット shall あるアドレスの受信を複数アドレスへの書き込みに展開する規則を、展開先の OSC アドレスのワイルドカードパターンで宣言する手段を提供する(要件書 R3-4、see D-13, D-15)。
3a. The Unity 参照実装 shall 適用範囲と展開先の双方で同一のワイルドカード一致規則を用いる(記法を 2 種類に分けない)(see D-15)。
4. When 案件ごとに異なるステージング構成(対象アドレス群・トリガ・展開規則)へ変更する, the Unity 参照実装 shall アセット定義の変更のみで当該構成を成立させる(C# ソースの変更を要求しない)(per plan S2-2)。
5. If ステージング宣言が不整合である(適用トリガの対象範囲にステージング対象が 1 つも解決できない、展開規則の展開先が解決できない等), the Unity 参照実装 shall 既存のアセット検証失敗と同じ扱いとしてエラーを記録し、マニフェストを送信しない(ping/pong・stats・エコーバックは継続する)。
6. Where ステージング宣言を一切持たないアセットが与えられる, the Unity 参照実装 shall 現行と同一の挙動(受信値の即時記録と同一アドレスへのエコーバック)を維持する。

### Requirement 2: ステージング対象アドレスの受信時挙動
**Objective:** オペレーターとして、スロットの各フィールドを編集した時点では UI 表示だけが確定し、アプリケーションへはまだ反映されない状態にしたい。それにより、レガシーの「Update を押すまで反映されない」運用感を再現できる。

#### Acceptance Criteria
1. When ステージング対象として宣言されたアドレスの値を受信する, the Unity 参照実装 shall 当該値をステージング領域へ保持する(要件書 R3-2)。
2. When ステージング対象として宣言されたアドレスの値を受信する, the Unity 参照実装 shall 同一アドレスへ受信引数をそのままエコーバックする(§3 の双方向同期の規律)(要件書 R3-2)。
3. When ステージング対象アドレスの値を受信する, the Unity 参照実装 shall アプリケーションへの適用イベントを発火しない(適用は適用トリガ受信時のみ)。
4. When ステージング対象アドレスの値を受信する, the Unity 参照実装 shall `currentValues`(マニフェスト `default` の供給源)を当該ステージング値で更新する(per plan S2-3、要件書 R3-2)。
5. The Unity 参照実装 shall ステージング対象アドレスの受信・エコーバックにおいて、ステージング対象でないアドレスと区別できる差分(応答アドレス・型タグ・追加メッセージ・遅延の有無)を発生させない(per plan S2-1)。
6. While 適用トリガを受信していない, the Unity 参照実装 shall ステージング値を保持し続け、アプリケーション側の適用済み値との乖離を許容する(要件書 R3-5)。

### Requirement 3: 適用トリガ受信による適用イベントの発火
**Objective:** アプリケーション実装者(Unity 側)として、Update ボタン受信時に対象範囲のステージング値をまとめて受け取りたい。それにより、キャラクターへの反映など案件固有の適用処理を自分の実装に閉じて書ける。

#### Acceptance Criteria
1. When 適用トリガとして宣言された button エントリのアドレスの値を受信する, the Unity 参照実装 shall 当該トリガの対象範囲に属するステージング値をアプリケーションへ引き渡す適用イベントを発火する(要件書 R3-3)。
1a. The Unity 参照実装 shall 適用イベントを C# の `event` として公開し、適用範囲のステージング値をアドレスと値の辞書として引数で渡す(`UnityEvent` によるインスペクタ結線は提供しない)(see D-11)。
1b. When 適用イベントを発火する, the Unity 参照実装 shall 適用範囲に属する全アドレスの現在のステージング値を渡す(前回適用からの差分に絞らない)(see D-16)。
2. The Unity 参照実装 shall 適用処理そのものを実装せず、適用イベントの購読者(アプリ固有実装)へ委ねる(要件書 R3-3)。
3. When 適用トリガのアドレスの値を受信する, the Unity 参照実装 shall 当該アドレスへも通常どおりエコーバックする(§3 の規律)。
4. When 適用イベントを発火する, the Unity 参照実装 shall 当該範囲のステージング値を破棄・リセットせず、保持したまま維持する(以降のマニフェスト `default` は同じ値を返す)(要件書 R3-5)。
5. If 適用トリガの対象範囲にステージング値が 1 件も存在しない, the Unity 参照実装 shall エラーとせずに処理を継続し、エコーバックを行う。
6. Where 適用トリガが全体適用(複数スロットを対象とする範囲)として宣言されている, the Unity 参照実装 shall 対象範囲に属する全ステージング値を 1 回の受信で引き渡す(要件書 §4.2 の Update All 相当)。

### Requirement 4: 一括操作の展開書き込みと個別エコーバック
**Objective:** オペレーターとして、「All」トグルの操作で全スロットの該当フィールドが一括で書き換わり、UI 上の各トグルもそれに追従してほしい。それにより、レガシーの All チェックボックス操作を再現できる。

#### Acceptance Criteria
1. When 展開規則の展開元として宣言されたアドレスの値を受信する, the Unity 参照実装 shall 当該規則が定める展開先の各アドレスのステージング値を受信値で書き換える(要件書 R3-4)。
2. When 展開書き込みを行う, the Unity 参照実装 shall 展開先の各アドレスへ個別にエコーバックする(UI の各ウィジェットが追従できるようにする)(要件書 R3-4)。
3. When 展開書き込みを行う, the Unity 参照実装 shall 展開先の各アドレスについて `currentValues` を更新する(再接続時のマニフェスト `default` に反映される)。
4. When 展開元アドレスの値を受信する, the Unity 参照実装 shall 展開元アドレス自身へも通常どおりエコーバックする(§3 の規律)。
5. When 展開書き込みを行う, the Unity 参照実装 shall 適用イベントを発火しない(展開はステージング値の書き換えにとどめ、適用は適用トリガ受信時のみ)。
6. If 展開先アドレスが別の展開規則の展開元でもある(規則が循環しうる), the Unity 参照実装 shall 展開を無限に連鎖させず、有限回で終了する。

### Requirement 5: 再接続時のステージング状態復元
**Objective:** オペレーターとして、ブラウザを開き直したり接続が回復した後も、まだ適用していない編集途中の値が UI に復元されてほしい。それにより、レガシーのローカル状態保存(`member_slot_state.json`)なしで「Unity が真実の源」の規律を保てる。

#### Acceptance Criteria
1. When マニフェストを生成する, the Unity 参照実装 shall ステージング対象エントリの `default` として、適用済み値ではなく現在のステージング値を出力する(per plan S2-3、要件書 R3-5)。
2. When マニフェスト要求を受信する, the Unity 参照実装 shall ステージング状態に関わらず、既存の応答規律どおり冪等に応答する(§2 の要求・再送・回復の仕様を変更しない)。
3. The Unity 参照実装 shall マニフェスト `default` の出力において、既存の値同期規律(`b` 型は対象外、`bool` は `i` の 0/1、値のない任意フィールドはキーごと省略し `null` を書かない)を維持する(per plan 全体コンテクスト)。

### Requirement 6: プロトコル・上位コンポーネント無改造の維持
**Objective:** OscDesk 本体の保守者として、ステージング追加によってワイヤプロトコル・ブリッジ・UI が影響を受けないことを保証したい。それにより、既存 UI・既存マニフェスト・既存テストを壊さずレガシー運用感を追加できる。

#### Acceptance Criteria
1. The Unity 参照実装 shall 生成するマニフェストを `version: 1` のまま出力する(per plan G-3)。
2. The Unity 参照実装 shall ステージング宣言(対象・適用トリガ・展開規則)をマニフェスト JSON へ出力しない(アセット内部の宣言に閉じる)(per plan S2-1)。
3. The 本仕様の実装 shall `packages/shared` のマニフェストスキーマ、`packages/bridge`、NiceGUI UI(`packages/nicegui-ui`)を変更しない(per plan S2-1, G-4)。
4. The Unity 参照実装 shall ステージングに関して新しい OSC アドレス・型タグ・メッセージ種別を追加しない(使用する OSC 機能は基本型タグ `i` / `f` / `s` / `b` と bundle / timetag のみ)(§4.4)。
5. If 実装中にステージングの実現がブリッジ・UI・プロトコルの変更を要すると判明した, the 実装担当 shall 独断で実装せず、差分と選択肢を添えてユーザー判断へ返す(CLAUDE.md の絶対規律、互換性ノートの記録方針)。

### Requirement 7: mock-unity のステージング模擬
**Objective:** 開発者およびフォーク側の E2E 作成者として、Unity 実機なしでステージング挙動を再現したい。それにより、ブリッジ〜UI 経由の「蓄えて Update で適用」の流れを自動テスト・手動検証できる。

#### Acceptance Criteria
1. The mock-unity shall ステージング機構を**汎用機構として実装**し(シナリオ固有の応答に留めない)、ステージング対象アドレス・適用トリガ・展開規則をシナリオで宣言できるようにする(see D-12)。
2. When mock-unity がステージング対象アドレスの値を受信する, the mock-unity shall 同一アドレスへエコーバックし、以降のマニフェスト応答の `default` に当該値を反映する。
3. When mock-unity が適用トリガのアドレスの値を受信する, the mock-unity shall 適用が発生したことを観測可能な形(適用済み値の保持または記録)で表現し、当該アドレスへエコーバックする。
4. When mock-unity が展開元アドレスの値を受信する, the mock-unity shall 展開先の各アドレスへ個別にエコーバックする。
5. The mock-unity のシナリオ shall upstream のテスト用に限定し、フォークのプリセットシナリオ(`vp-concert-default`)を含まない(per plan G-5)。
6. The mock-unity の既存シナリオ shall ステージング追加後も従来どおり(即時記録・即時エコーバック)動作する。

### Requirement 8: プロトコル文書の更新
**Objective:** プロトコル利用者(Unity 側実装者・フォーク側開発者)として、ステージングの実装指針を `docs/UNITY_PROTOCOL.md` で参照したい。それにより、特定 OSC ライブラリに依存しない形で自分の Unity 実装にステージングを組み込める。

#### Acceptance Criteria
1. The プロトコル文書(`docs/UNITY_PROTOCOL.md`)shall §4(実装指針)にステージング対象の受信時挙動(保持・エコーバック・`currentValues` 更新)、適用トリガによる適用イベント、展開書き込みの指針を含む。
2. The プロトコル文書 shall 付録 A(参照実装)の C# 全文をリポジトリ実ファイルと一致させる(既存の不変条件を維持する)。
3. The プロトコル文書 shall 互換性ノートに、ステージングがプロトコル無改造の Unity 側実装であり、ワイヤ上は通常のエコーバックと区別がつかないことを記録する(per plan S2-1)。
4. The プロトコル文書 shall ステージングが `/sys/*` プロトコルの必須要件ではなく、実装側の任意機構であることを明記する(ステージングを実装しない Unity 側も従来どおり適合する)。
5. The 検証手順書(`docs/VERIFICATION.md`)shall ステージング挙動の手動検証手順(編集時の表示確定と非適用、適用トリガでの適用、一括展開の追従、再接続時の復元)を含む。

### Requirement 9: 参照実装の検証可能性
**Objective:** 開発者として、Unity C# の参照実装に加えたステージング挙動を回帰検出できる形で検証したい。それにより、後続の変更で「蓄えて適用」の規律が静かに壊れることを防げる。

#### Acceptance Criteria
1. The 本仕様の実装 shall ステージングの中核挙動(保持・エコーバック・`currentValues` 更新・適用イベント発火・展開書き込み)を、mock-unity の自動テスト(`pnpm test` から実行)と Unity EditMode テストの**両方**で検証する(see D-12)。
2. The 本仕様の実装 shall ステージング規律の入力と期待出力を JSON の共通フィクスチャファイルとして持ち、mock-unity のテストと Unity EditMode テストの双方が同一フィクスチャを読んで判定する(see D-14)。
3. The 本仕様の実装 shall Unity EditMode テストの実行方法(`pnpm test` からは実行できず Unity Editor 経由になること)を文書化する。
4. The 本仕様の実装 shall `docs/VERIFICATION.md` に再現可能な手動検証手順(前提・操作・期待結果)を記載する。
5. The 本仕様の実装 shall 既存のテスト一式(`pnpm test`)を緑のまま維持する。

## Dig Summary

- ラウンド数: 3 / 質問数: 7 / 決定数: 7(D-10〜D-16)
- 主要な発見:
  1. 宣言記法は**ワイルドカードパターン 1 種類に統一**(D-15)。当初は適用範囲=前方一致・展開先=ワイルドカードの混在案だったが、アセット作成者が 2 規則を使い分ける書き間違いの温床になるため統一した
  2. 検証は mock-unity(汎用機構 + `pnpm test`)と Unity EditMode テストの**両方**を整備し、さらに JSON 共通フィクスチャを両者から読んで一致を機械担保する(D-12 / D-14)。この spec の作業量は当初想定より大きくなる
  3. 適用イベントは C# `event` で公開し、適用範囲の**全ステージング値**を辞書で渡す(D-11 / D-16)。差分方式は「どこまで適用済みか」の状態管理が増えるため採らない
- 決定一覧: 「Open Questions and Decisions (Dig)」の表を参照(D-10〜D-16)
- 残リスク(設計フェーズへ引き継ぎ):
  - ワイルドカード一致規則の厳密な定義(`*` が 1 階層のみに一致するか複数階層にまたがるか、末尾 `*` の扱い)が未定。設計で確定し文書化する
  - ステージング規律が C# と mock-unity(TypeScript)の 2 箇所に実装される二重管理。共通フィクスチャで緩和するが、C# 側から JSON を読む仕組みの新設が必要
  - EditMode テストは `pnpm test` から実行できないため、CI での自動実行は担保されない(Unity Editor を開く運用)
  - 展開規則の循環(展開先が別の規則の展開元でもある場合)の有限終了の実現方法が未定(要件 4.6)
